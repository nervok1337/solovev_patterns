# Сериализация хранилища

`storage.json` содержит все публичные свойства одного заполненного
`storage_manager`: коллекции `ranges`, `groups`, `warehouses`,
`nomenclatures`, `recipes` и признак `is_loaded`.
Имена свойств определяются через рефлексию, вложенные объекты раскрываются
конвертерами. Фабрика только выбирает подходящий конвертер.

Выгрузка содержит 5 единиц измерения, 3 группы, 3 склада, 4 номенклатуры
и 1 составной рецепт. Даты проверяются на тестовых моделях: в текущих
доменных моделях хранилища таких свойств нет.

## Повторная генерация

Выполнить из корня проекта:

```bash
.venv/bin/python -B - <<'PY'
import json
from pathlib import Path

from Src.Logics.convert_factory import convert_factory
from Src.Logics.storage_manager import storage_manager
from Src.Models.settings_model import settings_model

storage = storage_manager()
storage.convert(settings_model())
factory = convert_factory()
data = factory.create(storage).convert(storage)
content = json.dumps(data, ensure_ascii=False, indent=4, allow_nan=False)
Path("Docs/Serialization/storage.json").write_text(content + "\n", encoding="utf-8")
PY
```

Идентификаторы создаются моделями, поэтому при повторной генерации изменятся.
Единственное публичное свойство идентификатора сущности — `unique_code`.

## Представление базовой единицы измерения

Для единицы с коэффициентом 1, у которой `base_range` ссылается на неё саму,
в JSON сохраняется `"base_range": null`. Производная единица содержит полный
словарь базовой единицы с таким же завершающим значением `null`.
Правило реализовано в `range_convertor`, зарегистрированном в фабрике.
Общий конвертер составных объектов не содержит имён полей доменной модели.

В начальных данных грамм и миллилитр являются базовыми единицами
с коэффициентом 1. Килограмм содержит полный объект грамма, а литр —
полный объект миллилитра; коэффициент обеих производных единиц равен 1000.
У грамма и миллилитра в JSON поле `base_range` равно `null`.

Объекты в памяти при сериализации не меняются. При восстановлении базовой
единицы `null` передаётся конструктору как `None`: существующий `range_model`
сам возвращает связь `base_range` на созданный объект. Производная единица
получает уже восстановленный вложенный объект базы. Поиск объектов по ID
для этого не нужен. Обратное преобразование единиц проверяется тестами.

## Остальные циклические ссылки

Другие циклы приводят к явной ошибке преобразования. Они не заменяются
автоматически ни кодом объекта, ни `null`, поскольку это потеряло бы связь.

## Десериализация

Из корня проекта можно прочитать существующую выгрузку:

```bash
.venv/bin/python -B - <<'PY'
from Src.Logics.deserialize_factory import deserialize_factory
from Src.Logics.deserializer import deserializer
from Src.Logics.json_deserializer import json_deserializer

loader = json_deserializer(deserializer(deserialize_factory()))
loaded = loader.load_storage("Docs/Serialization/storage.json")
for recipe in loaded.recipes:
    print(recipe.name, recipe.gross_weight, recipe.net_weight)
    for item in recipe.ingredients:
        print("  ", type(item).__name__, item.name)
PY
```

`loaded` — контейнер `storage_data_dto` с настоящими доменными моделями.
Текущее singleton-хранилище автоматически не заменяется. Для строки JSON
используется `loader.loads_storage(text)`, для отдельной модели —
`loader.loads(text, recipe_model)` с явно переданным ожидаемым классом.
Поддержаны единицы измерения, группы, склады, номенклатуры, ингредиенты,
рецепты (включая вложенные) и отдельная организация.

Поток вызовов:

```text
JSON / файл
  → json_deserializer: разбор JSON
    → deserializer: контекст одной загрузки
      → abstract_deserialize_factory.create(ожидаемый тип)
        → обработчик категории: значение / коллекция / Union / объект
          → рефлексия конструктора и свойств → штатный конструктор
            → тот же контекст для вложенных значений (рекурсия)
```

Фабрика выбирает и создаёт обработчик, сама данные не преобразует.
Сервис восстановления зависит от абстрактной фабрики из Core; конкретную
фабрику передаёт вызывающий код. Модели не зависят от JSON, файлов или
десериализаторов. Проверки бизнес-ограничений остаются в конструкторах моделей.
Каждый класс десериализации находится в отдельном одноимённом файле.
В `deserialize_factory.py` находится только фабрика; обработчики импортируются
из своих модулей. Абстрактные контракты и контекст восстановления также разделены.
В фабрике нет списка доменных классов и ручных схем их полей.

`reference_deserializer` получает свойства через `common.get_fields(класс)`,
параметры конструктора через `inspect.signature`, а типы через
`typing.get_type_hints`. Для заполнения используются обычный конструктор
и публичные сеттеры; приватные поля не записываются в обход проверок.
Вычисляемые свойства без сеттера сверяются с данными после создания объекта.

Тот же механизм принимает DTO без `name`, `unique_code` и наследования от
`entity_model`. Например:

```python
from Src.Dtos.report_row_dto import report_row_dto

row = loader.loads('{"values": [12, "пример", null]}', report_row_dto)
print(row.values)
```

Для нового класса не требуется менять фабрику: нужны аннотации типов
параметров конструктора и сериализуемых свойств. Поддержаны также публичные
аннотированные атрибуты, например поля dataclass. Имена JSON-полей должны
соответствовать именам параметров и свойств. Обязательные параметры должны
присутствовать, для пропущенных необязательных действуют значения конструктора.

Тип элементов коллекции берётся из её аннотации. Для `Union` выбирается
единственный вариант, соответствующий структуре данных; если вариантов
несколько, возникает явная ошибка. Например, ингредиент и вложенный рецепт
различаются свойствами, полученными рефлексией, без проверки конкретного имени
поля в коде десериализатора. `Any` и `object` сохраняют обычные JSON-значения:
без информации о целевом типе восстановить произвольный класс невозможно.

Формат выгрузки сохранён: вложенные сущности представлены полными объектами.
В рамках одной загрузки равные сущности с одинаковыми данными
возвращают уже созданный экземпляр. Используется существующий контракт
`entity_model.__eq__`, сравнивающий `unique_code`; десериализатор не читает
это поле по имени. Для обычных DTO такой контракт не требуется.
Поэтому ингредиент ссылается на ту же
номенклатуру, которая находится в `loaded.nomenclatures`. Контекст нужен
для сохранения идентичности повторных объектов, а не для разрешения ссылок
вида ID в JSON. Каждая новая загрузка создаёт независимый граф моделей.

Для базовой единицы `base_range: null` восстанавливает самоссылку через
существующий конструктор. Произвольные циклы не поддерживаются, как и при
сериализации. Неверные поля, противоречивые определения одного кода и
несовпадение сохранённого веса рецепта с его составом вызывают ошибку.
Вес рецепта вычисляет сама модель, десериализатор его не присваивает.

Проверка: `.venv/bin/python -B -m pytest Tst/Unit/test_deserialization.py -q`.
Тесты сохраняют модели из `storage_manager` во временный файл, загружают его
и сравнивают все сериализуемые поля, типы и общие ссылки. Также проверяются
чтение приложенного `storage.json`, существующий DTO отчёта без идентификатора,
новый вложенный DTO без регистрации в фабрике, наследование свойств,
неоднозначный Union и отклонение некорректных данных.
